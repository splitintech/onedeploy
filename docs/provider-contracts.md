# Provider transport contracts

Status: **experimental/offline-tested**, not staging-qualified. No cloud deployment, login, resource creation, or credential creation was performed during implementation. Contract fixtures validate construction and parsing, not live behavior. Provider acceptance, running state, readiness, ingress authentication and application qualification are separate layers.

## Importers do not expand provider capabilities

The experimental wizard and JSON `discover → resolve → plan` path feed these same adapters. [Importer recognition](IMPORTERS.md) is separate from provider/profile support. A Compose service is not automatically a multi-service deployment; a Dockerfile is not a Modal ASGI entrypoint; detecting an application name does not establish an authenticated target. Exact identity and remote preconditions are checked only after explicit read-only inspection.

`doctor` reports local executable/SDK/version prerequisites, not login state. The wizard labels authentication as unchecked until the operator requests remote inspection. Missing tools and authentication require deliberate operator setup using the official references below; Onedeploy never silently installs a CLI, logs in, creates tokens or saves credentials.

## Adapter API

`get_adapter(name)` returns `validate(manifest)`, `plan(manifest)` (`plan_steps` alias), `command(manifest, operation)`, `parse(operation, stdout)`, `assert_target(manifest, identity, inspection)`, and `rollback_steps(manifest, release)`. Capability metadata is JSON serializable. Commands are immutable data for the core runner, never an execution shortcut.

Steps contain `id`, `argv`, `mutating`, and `env_keys`. Runtime values are resolved by the core only: `stdin_env_keys` with `stdin_format: raw` sends one value; `stdin_format: json` sends a string map. `runtime_env_keys` passes only resolved application variables, not ambient environment. All Railway reads/writes use explicit project/environment selection and do not require linking. All uploads execute from the core's sanitized source bundle. No manifest executable, API URL, shell program, or credential-path override is supported.

Inspection precedes approval and is repeated before mutation. Malformed responses, wrong accounts, absent required identity fields, and changed resource generations fail closed. A timeout/nonzero exit during mutation is uncertain, not proof of no effects. Reconciliation reads only. The operator must resolve an ambiguous outcome before a new plan; no automatic write replay occurs.

## Railway

Target fields: `account` (authenticated user email or user ID), `project`, `environment`, and `service` (IDs, not ambiguous names). Every relevant command explicitly selects the project/environment; Onedeploy never creates or changes a local project link. `RAILWAY_API_TOKEN` or an existing saved login is supported. Project-token-only identity is not qualified.

Profiles: `docker-http`, `asgi`, `worker`. The source root uses `Dockerfile`; custom build roots and manifest startup overrides are rejected. The reviewed Dockerfile/provider configuration owns startup. Resource changes and private ingress requests are rejected; `ingress.mode: existing` preserves existing exposure. HTTP path/port metadata does not by itself reconfigure Railway.

Each application variable is transmitted by `railway variable set KEY --stdin --skip-deploys`, explicitly selecting project, service and environment. Then `railway up . --project ID --service ID --environment ID --ci --json` uploads the sanitized source. A successful command is not a readiness claim. Identity uses `whoami --json`; resource inspection uses `status --json`; logs use an explicit target and 100-line limit. Inspection strips secret-bearing and unrecognized fields. Known-artifact rollback reuploads a locally retained, reviewed sanitized bundle with its prior configuration through a separately approved plan. It never treats the latest-deployment redeploy command as a historical rollback.

Official references checked 2026-10-23: [up](https://docs.railway.com/cli/up), [variable](https://docs.railway.com/cli/variable), [status](https://docs.railway.com/cli/status), [whoami](https://docs.railway.com/cli/whoami), [logs](https://docs.railway.com/cli/logs). Pinned CLI contract: `@railway/cli@5.71.0`; its official Linux release binary was executed locally for version and help only. Actual help additionally verifies `--project` for variable set and status (the web reference omits those flags). Live contract qualification remains required before relying on a new CLI version.

## Daytona

Install the optional, exact `daytona==0.226.0` SDK. The isolated bridge checks this version, uses only `DAYTONA_API_KEY`, and fixes the API origin to `https://app.daytona.io/api`. A credential-bearing HTTP redirect is rejected. Runtime values enter stdin; a temporary empty working directory prevents implicit project dotenv loading. SDK output and exception text are suppressed because they may contain credentials. Identity is the organization returned by the authenticated current-key endpoint, not the requested organization echoed back.

Targets: `account` (organization ID), `sandbox` (unique name or existing ID), `mode: create|existing`, optional `snapshot`, `region: us|eu`. Create requires a unique sandbox name and either an existing reviewed snapshot or an explicit project snapshot build. Its precondition binds snapshot ID, immutable `@sha256` image digest, and absence of that sandbox. Mutable image tags are rejected; creation uses the resolved snapshot ID, not its mutable name. For an existing snapshot, the local source inventory binds operator configuration, not the snapshot's separately built application source. For project builds, the actual sanitized bundle is the snapshot build context. It uses `CreateSandboxFromSnapshotParams`, private ingress, explicit auto-stop policy, and no automatic deletion. CPU/memory/disk are inherited from the snapshot. Existing mode starts the same sandbox, does not replace code/configuration, and refuses runtime-variable/resource edits. Existing private ingress must be observed private. No volume creation, DNS, stable browser OAuth origin, or deletion is hidden in this path.

Snapshot startup is responsible for the application; a sandbox in `started` state alone proves no application readiness. Explicit verification uses a fixed, bounded `python3 -I` localhost GET probe, with shell-quoted port/path data and no response-body retention. It requires Python in the snapshot and distinguishes health from readiness. Entrypoint logs use the supported SDK read and are capped for display. Redaction remains best-effort. Signed previews are not issued or persisted.

Official references: [SDK create/get models](https://www.daytona.io/docs/en/python-sdk/sync/daytona/), [sandbox lifecycle](https://www.daytona.io/docs/en/python-sdk/sync/sandbox/), [process/logs](https://www.daytona.io/docs/en/python-sdk/sync/process/), [authentication](https://www.daytona.io/docs/en/authentication/), [current API key](https://www.daytona.io/docs/api-keys/). The SDK and generated API wheel interfaces were inspected offline; transport tests inject only the SDK boundary.

## Modal

CLI compatibility target: `modal==1.6.2`. Target fields: `account` (workspace slug), `environment`, `app` (name), optional `function` (HTTP function name), and optional `mode: create|existing`. Identity requires one active, authenticated saved Modal profile; environment-token override workflows are deliberately not used. Existing mode checks the named app; create mode proves its name absent in an explicitly scoped app list before deployment.

Only the `asgi` profile is implemented. `source.entrypoint` is a relative `.py` file. `source.trust_code: true` acknowledges that Modal imports and executes this source locally with the invoking user's permissions. This is not a security sandbox. Image, resources and endpoint authentication must be declared in that reviewed source. Application variables reach only the deploy process environment; the source must deliberately use them (for example, an explicit `modal.Secret.from_dict` mapping). Generic resource/build settings and requests for private networking are rejected. The generic template uses Modal proxy authentication, which is different from private networking.

Deployment uses `modal deploy ENTRY --name APP --env ENV`. Read operations use `profile list --json`, `app info --json`, and bounded `app logs --tail 100`. `app info` includes lifecycle version, not an endpoint URL; no URL is guessed. For Railway, an explicit `runtime.ready_url` may select a credential-free official-provider HTTPS origin (no path; set `runtime.ready_path` separately), but only when its hostname also belongs to the observed target service/environment. Probes reject redirects/private IPs and do not establish authentication policy. Modal endpoint inspection uses `modal function info APP/FUNCTION --env ENV --json`; the returned app ID, function ID and function name must match the observed application. Only that function's official endpoint origin can be probed. An unrelated configured origin is never accepted. Protected endpoints can legitimately return authentication-required without passing readiness; no authentication token is forwarded by the public probe. Specific `vN` rollbacks use `modal app rollback APP vN --env ENV` in a separately approved plan. Provider account-tier restrictions may reject rollback; data/schema changes are never undone.

Official references: [deploy](https://modal.com/docs/cli/latest/deploy), [app operations](https://modal.com/docs/cli/latest/app), [profile](https://modal.com/docs/cli/latest/profile), [rollback semantics](https://modal.com/docs/guide/managing-deployments). CLI JSON field names and proxy-auth option were additionally inspected in the pinned SDK wheel.

## Remaining operator qualification

Run opt-in staging against dedicated resources only after installing the documented interfaces, reviewing the exact plan, and supplying credentials locally. Record versions, target identities, source digest, sanitized observations, deployment IDs, readiness/auth results, interruption reconciliation, and rollback outcome. Never record runtime values, provider tokens, signed preview URLs, or private source. Cost estimates are not spending caps, auto-stop is not deletion, and source publication is not permission to deploy.

## Version preflight

Adapters expose `version_command()` and `parse_version(stdout)` for the core doctor/preflight. A mismatch with Railway 5.71.0, Modal 1.6.2 or Daytona 0.226.0 fails closed. The Daytona bridge additionally enforces its exact SDK pin before cloud operations. Installing or upgrading provider tools is always an explicit operator task.

### Pinned Railway response evidence

The v5.71.0 [status implementation](https://github.com/railwayapp/cli/blob/v5.71.0/src/commands/status.rs) and [environment-instance query](https://github.com/railwayapp/cli/blob/v5.71.0/src/gql/queries/strings/EnvironmentInstances.graphql) establish that service instances live under environment nodes. The parser verifies the service's actual target-environment instance, retains deployment ID/status and generated Railway domains, and discards raw command text, source configuration, deployment metadata and custom domains. Relevant service configuration is HMAC-bound with the local state key, so startup/build/resource overrides cannot silently change between approval and mutation. A single observed `*.up.railway.app` domain can supply the explicit ready-path probe; ambiguous domains require `runtime.ready_url`. The transport never creates a domain.

### Accepted-release attribution

Railway deployment parsing consumes the pinned CLI JSON stream and records the final `deploymentId` as `deployment_id`, along with target IDs. Subsequent status must match that accepted ID; merely observing a different deployment than before is insufficient. Daytona creation/start records the SDK-returned resource ID. Modal deploy uses a plan-bound `--tag`; `app history --json` provides version/tag correlation. Exactly one matching tag is required, and the tag must not already exist before execution. Its correlated version must equal the currently observed lifecycle version. Raw CLI completion alone still records `release_binding: unavailable`; without successful history correlation a newer observed version is only an unbound candidate. Reviewed tagged prior releases make explicit rollback executable; rollback creates a new version but exposes no new-version receipt or tag, so post-rollback generation remains unbound rather than guessed. No readiness layer may be promoted from an unrelated healthy endpoint. See the [pinned Railway result producer](https://github.com/railwayapp/cli/blob/v5.71.0/src/commands/up.rs).

Modal tag and endpoint contracts were checked against the official [deploy](https://modal.com/docs/cli/latest/deploy), [history](https://modal.com/docs/cli/latest/app) and [function info](https://modal.com/docs/cli/latest/function) references and the 1.6.2 wheel. History JSON uses `version`/`tag`; function JSON uses `app_id`, `object_id`, `name`, and `web_info.web_url`/`unauthenticated`. The public `App.deploy` SDK method returns the App rather than a release receipt; no private RPC was added.

## Project snapshot builds and existing storage

Daytona project build manifests use `build: {context: ".", dockerfile: "Dockerfile", snapshot_name: "unique-new-name"}` with `target.mode: create` and no `target.snapshot`. The source is the core's sanitized bundle, not the original working directory. A separate journaled `snapshot-create` operation calls the pinned public `Image.from_dockerfile(path, strict_context=True)` and `snapshot.create(CreateSnapshotParams(name, image), timeout=...)`. Runtime secrets are not sent to this operation. Dockerfile network accesses and package downloads are part of the reviewed build, not a hermetic-build guarantee. The resulting snapshot ID and immutable image digest are retained. Only a successful receipt may materialize the later create operation; a mutable name alone cannot authorize it. Existing snapshot names and uncertain builds are never automatically replayed. Snapshots retain storage and may incur cost even if later sandbox creation fails; no cleanup deletes recovery artifacts automatically.

Existing storage is declared as `storage: [{name: "cache", resource_id: "existing-resource", mount_path: "/cache", kind: "model-cache", access: "read-write", single_writer: false}]`. No provider volume is created. Daytona resolves `resource_id` as a volume **name** using `volume.get(name, create=False)`, verifies organization and ready state, and passes the returned immutable ID to `VolumeMount` on new sandbox creation. These are shared read-write mounts; read-only or exclusive-single-writer guarantees are not available from the pinned mount interface and are rejected rather than asserted. Application concurrency coordination remains necessary. Cache volume storage persists beyond sandbox lifecycle.

Railway uses volume **IDs** and additionally requires `attachment: "attach"` or `"existing"`, `access: "read-write"`, and `single_writer: true`. Existing mode verifies the target service/environment and inherited mount path without mutation. Attach requires a detached existing volume with the exact requested mount path, then journals `railway volume --project P --environment E --service S attach --volume V --yes --json`. It never detaches another service, reassigns storage, changes mount paths, or deletes data. The inspection transition is allowed only for that successful attachment receipt. Single-writer requests also require one observed service replica. This does not prove there is only one application process writing inside that replica; application-level concurrency control remains necessary.

The pinned public [Railway volume implementation](https://github.com/railwayapp/cli/blob/v5.71.0/src/commands/volume.rs) and locally executed help confirm the attachment flags and JSON success receipt. Daytona contracts were checked in the official 0.226.0 wheel: `common/image.py`, `common/snapshot.py`, `_sync/snapshot.py`, `_sync/volume.py`, and generated `SandboxVolume`/`VolumeState` models. Contract tests inject SDK objects; no cloud build or storage mutation was performed during implementation.

`materialize_step(step, completed_operations)` is a pure transform of a planned command using successful immutable artifact receipts. `assert_preconditions(manifest, planned, observed, completed_operations)` permits only the exact snapshot or attachment transition justified by those receipts. Neither helper executes code or treats failed/uncertain journal entries as successful.

### Known-artifact recovery boundaries

Railway rollback selects a prior local deployment record, verifies its retained sanitized source artifact and configuration binding, then performs a new deploy of that artifact. It is not a remote deployment-ID rollback, and does not reverse schema changes or external side effects. Existing volume mounts remain attached; old data is neither restored nor erased.

Daytona rollback requires an explicit new replacement sandbox name and a known prior `snapshot_id`/`snapshot_image` receipt. A separate plan inspects that immutable artifact, proves the replacement name absent, and creates it privately with reviewed configuration. The bridge compares the exact snapshot receipt again before creation. The old sandbox and snapshots are retained; no traffic cutover, deletion, shared-data rollback, or exclusive cache-writer claim is implied. Running both sandboxes can increase costs and requires explicit application concurrency discipline.

### Daytona declared application checks

The `verify-checks` read-only command executes a constant bounded localhost HTTP probe via the documented `sandbox.process.exec(command, env=..., timeout=...)` interface. Only validated GET paths/status contracts enter command arguments. Referenced bearer values arrive at the bridge on stdin and enter the remote probe through the SDK environment map, never command arguments or files. Negative unauthenticated denial and positive bearer success must both match when auth evidence is requested. Responses are status-only and redirects are not followed. This proves the declared local application route contract, not an internet-facing ingress policy; the sandbox remains private. At most eight checks are permitted with a bounded overall process timeout. No arbitrary lifecycle hook or mutation is inferred from these checks.

### Provider-specific intent validation

Container providers reject `source.entrypoint`; startup is artifact-owned. Modal rejects `runtime.command` and requires `target.function` before any HTTP health, readiness, configured endpoint, or application check can be planned. Railway rejects Daytona-only `build.snapshot_name`; Daytona rejects Railway-only storage attachment modes. An existing Daytona sandbox may assert its exact observed snapshot but cannot request new region placement. Daytona does not accept external `runtime.ready_url` origins.

`runtime.port` is descriptive listener metadata for Railway/Modal, not a request to change provider routing or application startup. Those must be configured in the reviewed Dockerfile/provider settings or Modal Python source. On Daytona, port is the actual localhost probe destination. `source.trust_code` outside Modal is an optional operator trust assertion, not a command or lifecycle hook. Provider-irrelevant target keys and resource edits are rejected rather than ignored.
